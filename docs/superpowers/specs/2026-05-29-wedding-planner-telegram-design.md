# Дизайн: Telegram-нативный планировщик свадьбы (РФ)

**Дата:** 2026-05-29
**Статус:** утверждён (brainstorming → готов к плану реализации)
**Рабочее имя:** m-planner

---

## 0. Контекст и позиционирование

Продукт для российского (в первую очередь московского) рынка планирования свадеб.
Опирается на три внутренних документа исследования:

- `audience-research.docx` — боли ЦА, проранжированные по severity.
- `competitor-analysis.docx` — разбор planning.wedding и рынка РФ.
- `market-sizing.md` — TAM/SAM/SOM, юнит-экономика, каналы.

**Ключевые выводы исследования, определившие дизайн:**

- Топ-2 боли (обе 9/10): **доверие к подрядчикам** (кидают/молчат) и **непрозрачность цен** (смету нельзя спрогнозировать).
- Деньги — не в подписке пары (свадьба разовая, LTV короткий), а в монетизации supply (комиссия/лиды) и безопасной сделке. Фокус старта — **acquisition + referral**, не выручка.
- Дистрибуция — **Telegram**, не SEO (конкуренты собирают всего ~100–140k визитов/мес, инструментов в TG нет).
- Рынок в штуках сжимается (~880k браков, тренд вниз), в деньгах растёт (+20%/год, средний чек >2 млн ₽).
- planning.wedding задаёт планку по широте инструментов, но не локализован под РФ: нет ЗАГС, нет ₽-смет, нет российских подрядчиков, нет Telegram.

**Позиционирование:** «Российский планировщик свадьбы в Telegram» — закрывает не красоту, а главную боль: **не потерять деньги, нервы и дату**.

## 1. Стратегия и дорожная карта

Три опоры дифференциации реализуются **как фазы, а не как один релиз**:

| Фаза | Что | Боли | Монетизация |
|------|-----|------|-------------|
| **0** | Смета-крючок: ввёл формат+город+гостей → реальная ₽-смета по Москве за 2 минуты | №2 (9/10) | нет |
| **1** | Планировщик: смета → трекер бюджета+платежи → делегирование невесте → ЗАГС/таймлайн-чеклист | №2,3,4 | нет |
| **2** | Доверие: верификация подрядчиков, рейтинг по реальным заказам, чёрный список, безопасная сделка 3–7%, бизнес-портал | №1 (9/10) | **да** |

**Логика последовательности:** нельзя строить слой доверия к подрядчикам (фаза 2), пока нет аудитории пар (фазы 0–1). Сначала собираем спрос бесплатной пользой, потом монетизируем supply.

**Граница этого спека:** Фаза 0 + ядро Фазы 1. Фаза 2 — отдельный спек-цикл позже. Архитектуру v1 закладываем так, чтобы она доросла до Фазы 2.

### Объём v1

**Входит:** смета → трекер бюджета и платежей → делегирование партнёру → ЗАГС/таймлайн-чеклист с напоминаниями. **+ по итогам CEO-ревью:** вирусная петля шеринга сметы, публичная витрина «реальные сметы», камерный режим (анти-classic). Подробности — раздел 11.

**НЕ входит (YAGNI):** каталог/верификация подрядчиков, безопасная сделка, рейтинги/чёрный список (всё это — Фаза 2; чёрный список lite сознательно отложен из-за юр-рисков и потребности в supply), список гостей/RSVP, рассадка, сайт-приглашение, AI, мультигород сверх МСК/СПб.

## 2. Общая архитектура

Монорепо (pnpm workspaces + Turborepo). Единый язык — TypeScript на всех приложениях (miniapp/api/bot), общие доменные типы и zod-схемы в `packages/shared`: одна модель данных проходит сквозь весь стек без переводов между языками, меньше рассинхрона контрактов.

```
m-planner/
├── apps/
│   ├── miniapp/   # Next.js — Telegram Mini App (основной UX)
│   │              #   + публичные SSR-роуты /showcase, /s/<preset> (Eng §12.1)
│   ├── api/       # NestJS — REST API, домен, бизнес-логика
│   └── bot/       # grammY — напоминания, шаринг, deep-links
├── packages/
│   ├── shared/    # TS-типы, zod-схемы, доменные value-objects (вкл. Money)
│   └── db/        # Prisma schema + миграции
└── infra/         # docker-compose: postgres, redis
```

- **Хранилище:** PostgreSQL.
- **Очередь/напоминания:** Redis + BullMQ (отложенные jobs).
- **Хостинг:** Docker на собственном сервере.
- **Форма доставки:** Mini App — основной UX; бот — уведомления и шаринг.

### Аутентификация

1. Mini App передаёт `initData` в API.
2. API валидирует HMAC-подпись `initData` по токену бота (стандарт Telegram Mini Apps).
3. При успехе — upsert `users` по `telegram_id`, выдача session-JWT.
4. Бот и Mini App делят одну таблицу `users` (ключ — `telegram_id`).
5. Невалидный `initData` → 401.

### Мост Фаза 0 → Фаза 1

Модель данных проектов закладывается сразу. Смета (Фаза 0) работает **анонимно, без сохранения** — только считает. У результата есть CTA «Сохранить как бюджет» → создаётся `wedding_project` с предзаполненными `budget_items` из категорий сметы. Это переход 0→1 без переписывания кода.

## 3. Доменные контексты (DDD)

Пять изолированных bounded contexts:

1. **Identity & Project** — `User`, `WeddingProject`, `ProjectMember`.
2. **Estimate (смета)** — `Category`, `PriceBenchmark`, расчёт сметы.
3. **Budget** — `BudgetItem`, `Payment`.
4. **Checklist/Timeline** — `ChecklistTemplate`, `ChecklistItem`.
5. **Notification** — отложенные напоминания через бот (BullMQ).

Каждый контекст — отдельный модуль NestJS с типизированным публичным интерфейсом. Файлы < 500 строк.

## 4. Модель данных

```
users(id, telegram_id UNIQUE, name, tz DEFAULT 'Europe/Moscow', created_at)

wedding_projects(id, owner_id → users, city, wedding_date,
                 format [zags|vyezdnaya|kamernaya], guest_count,
                 tier [budget|mid|premium], zags_application_date, created_at)

project_members(project_id → wedding_projects, user_id → users, role [owner|partner],
                PRIMARY KEY (project_id, user_id))

categories(id, slug UNIQUE, name, unit [per_guest|fixed], sort)

price_benchmarks(category_id → categories, city, tier, source [seed|crowd],
                 p25, median, p75, sample_count, updated_at,
                 PRIMARY KEY (category_id, city, tier, source))

budget_items(id, project_id → wedding_projects, category_id → categories,
             vendor_name, planned_amount, status)

payments(id, budget_item_id → budget_items, type [prepay|balance|full],
         amount, due_date, paid_at, payer [couple|parents|other])

spend_facts(id, category_id → categories, city, tier, guest_count, amount, created_at)

checklist_templates(key PRIMARY KEY, title, kind [zags|vendor|general],
                    offset_days_before_wedding)

checklist_items(id, project_id → wedding_projects, template_key → checklist_templates,
                title, due_date, done, reminder_at)
```

- `spend_facts` — реальные траты, источник для crowd-бенчмарков. **Eng §12.7:** ровно один факт на `(project_id, category_id)` (UNIQUE, upsert по итоговой сумме). `project_id` хранится только для upsert/удаления и **никогда не попадает в агрегаты** — это даёт исполнимое право на удаление по 152-ФЗ и снимает дубли. Анонимность выдачи держит k-anon-порог.
- Все суммы — **целые копейки (`bigint`)** по всему стеку (БД, домен, API); форматирование в ₽ только на границе UI через единый тип `Money` в `packages/shared`. Никакого float/numeric. Валюта только ₽ в v1. (Eng §12.5)

## 5. Потоки данных

### 5.1 Смета (Фаза 0)

1. Ввод `city, format, guests, tier`.
2. API по каждой категории берёт `price_benchmarks` и считает: `unit=per_guest → median × guests`, `unit=fixed → median`.
3. Возвращает по категории диапазон (p25–p75) и итог.
4. Если `crowd.sample_count ≥ N_threshold` — показываем crowd с подписью «**медиана по N реальным свадьбам**»; иначе seed.
5. CTA «Сохранить как бюджет» → создание `wedding_project` + `budget_items` по категориям.

### 5.2 Бюджет (Фаза 1)

1. Статьи (`budget_items`) с подрядчиком и планом.
2. Платежи (`payments`): предоплата/остаток/полный, сумма, дедлайн, кто платит.
3. При вводе суммы платежа → запись `spend_fact` → асинхронный джоб пересчитывает агрегат категории.

**Это flywheel:** трекер кормит смету реальными цифрами → смета приводит новые пары в трекер.

### 5.3 Делегирование

Owner генерирует инвайт-ссылку `t.me/<bot>?startapp=invite_<token>` → партнёр открывает → добавляется в `project_members` с ролью `partner`.

### 5.4 ЗАГС / таймлайн

При создании проекта инстанцируем `checklist_items` из `checklist_templates`, привязывая к `wedding_date` через `offset_days_before_wedding` (напр. «подать заявление в ЗАГС», список документов, бронь подрядчиков за 6 мес.). `reminder_at` ставится в BullMQ → бот шлёт пуш.

---

## 6. Crowd-агрегация

- Джоб (по записи `spend_fact` / ночью) считает `median, p25, p75` по `(category, city, tier)` где `count ≥ N_threshold` → пишет `price_benchmarks(source=crowd)`.
- Защита от мусора: винзоризация выбросов, игнор нулей/абсурдных значений, минимальный порог выборки.
- Без ML и сложной модерации — объёмы на старте малы.
- Правило показа: crowd при `sample_count ≥ N_threshold`, иначе seed. Пусто не показываем никогда.

## 7. Краевые случаи

| Случай | Поведение |
|--------|-----------|
| Невалидный `initData` | 401 |
| Нет бенчмарка по категории | fallback на seed |
| Валюта | только ₽ в v1 |
| Совместное редактирование | last-write-wins по полям (без CRDT в v1) |
| Часовой пояс напоминаний | дефолт МСК; поле `users.tz` на будущее |
| Crowd-выбросы | винзоризация + порог выборки |

## 9. Сидинг данных

`price_benchmarks(source=seed)` заполняется вручную из исследования ЦА (ориентиры: банкет ~5000 ₽/чел, средняя свадьба Москва от 700к, средний бюджет 2026 >2 млн ₽), разбитыми по `категория × город (МСК/СПб) × tier (budget/mid/premium)`.
`checklist_templates` заполняются российскими вехами: ЗАГС/Госуслуги (подача заявления, сроки, документы), бронь подрядчиков по срокам (фотограф/ведущий за 6 мес., платье за 3 мес.).

## 11. Ревизия по итогам CEO-ревью (2026-05-29)

Принятый подход: **A — полный v1**. Режим: **SELECTIVE EXPANSION**. Линза v1: продукт живёт ради **виральности + сбора данных** (моат — реальные траты), монетизация честно отложена в Фазу 2.

### 11.1 Вирусная петля шеринга сметы (принято в v1)

После расчёта сметы — кнопка «Поделиться»: генерится Telegram-карточка «Смета свадьбы в Москве: ~X₽» + deep-link на запуск Mini App с пресетом параметров. Это несущий механизм acquisition, без него стратегия захвата не работает. Шеринг доступен и из анонимной сметы (Фаза 0, без сохранения).

### 11.2 Публичная витрина «реальные сметы» (принято в v1)

Отдельный экран: анонимные агрегаты «реальные сметы пар в Москве», медиана/диапазон по городу и формату. Соцдоказательство (боль №2) + органический канал. Кормится из `spend_facts`. Доступ публичный (неаутентифицированный роут) → см. 11.5 и 11.7.

### 11.3 Камерный режим / анти-classic (принято в v1)

Тумблер формата `kamernaya` (уже в модели) перекраивает смету (убирает тамаду/выкуп/большой банкет) и подменяет ветку `checklist_templates`. Дешёвая дифференциация, боль №5, недообслуженный сегмент.

### 11.4 152-ФЗ / персональные данные (КРИТИЧНО, принято)

- Хостинг и БД с перс.данными граждан РФ — на серверах в РФ.
- Экран согласия на обработку перс.данных при первом входе; ссылка на политику обработки.
- Минимизация данных: не хранить лишнего; `spend_facts` обезличены (нет FK на пользователя).
- Право на удаление: пользователь может удалить проект и связанные перс.данные.

### 11.5 Надёжность напоминаний (КРИТИЧНО, принято)

Промах напоминания = пропущенная дата ЗАГС = сломано ядро обещания. Поэтому:
- Доставка через бот: ретраи с экспоненциальным бэкоффом; обработка Telegram 429 и «бот заблокирован пользователем».
- Поле статуса доставки у напоминания (`sent|failed|blocked`).
- **Видимый фоллбэк:** критичные дедлайны (ЗАГС, платежи) всегда продублированы в Mini App, а не только в пуше.
- Метрика `reminders_sent / reminders_failed` (см. 11.8).

### 11.6 k-анонимность агрегатов (принято)

Единый порог `N_threshold` применяется к показу **любых** агрегатов — и crowd-вилок в смете, и публичной витрины (11.2). Ниже порога по срезу `(category, city, tier/format)` — показываем seed или «недостаточно данных», но никогда не раскрываем малую выборку. Защищает от деанонимизации реальных трат и от вводящих в заблуждение цифр.

### 11.7 Безопасность инвайт-токена (принято)

Инвайт-ссылка делегирования даёт доступ к финансам проекта, поэтому токен:
- длинный, криптослучайный (не угадывается);
- с истечением (см. раздел 10) и возможностью отзыва владельцем;
- привязан к одному проекту и роли `partner`;
- одноразовое связывание: после принятия инвайта токен инвалидируется.

### 11.8 Observability (принято как следствие 11.5)

Метрики: `reminders_sent/failed/blocked`, конверсия `смета → сохранение проекта`, шеры сметы, объём `spend_facts` по срезам. Лог входа/выхода ключевых codepath (смета-расчёт, создание проекта, доставка напоминания).

### 11.9 Отложено в TODOS

- **Чёрный список подрядчиков (lite)** — намёк на боль №1, но Фаза-2 территория: юр-риски (диффамация) + нужен supply. Не в v1.

### Verdict CEO-ревью

Стратегия и объём v1 утверждены. Клин (прозрачность цен + петля данных) бьёт в боль 9/10, обходит «курицу-яйцо» доверия, и пользователь сам пользуется на своей свадьбе. Готово к Eng-ревью архитектуры.

## 12. Ревизия по итогам Eng-ревью (2026-05-29)

Объём v1 подтверждён **полным одним куском** (не режем). Ниже — архитектурные/технические решения ревью; они уточняют, но не расширяют объём.

### 12.1 Публичная web-поверхность (Архитектура)

Mini App рендерится только внутри Telegram. Витрина (11.2) и лендинг share-карточки (11.1) — это **публичные SSR-роуты в том же `apps/miniapp`**:
- `/showcase` — индексируемая витрина «реальные сметы» (органический канал).
- `/s/<preset>` — OG-лендинг share-карточки с CTA «Открыть в Telegram» → `t.me/<bot>?startapp=...`.
Оба читают агрегаты через ту же k-anon-границу (12.2). Отдельный `apps/web` не заводим — лишний деплой.

### 12.2 Единый `BenchmarkReader` (Архитектура / DRY / приватность)

Все три read-пути к агрегатам (смета, `/showcase`, OG-лендинг) ходят **только** через один доменный сервис в контексте Estimate. Сырой `price_benchmarks` наружу не выходит. Он же — единственная точка применения k-anon-порога (11.6): `count < N_threshold` → seed или «недостаточно данных», никогда не raw малая выборка.

### 12.3 Anti-replay и жизненный цикл токенов (Безопасность)

Валидация `initData`: HMAC-подпись **+ проверка `auth_date`** (не старше окна, напр. 24ч) → отклоняем старые/повторные. session-JWT короткоживущий (напр. 1ч); при истечении Mini App переотправляет свежий `initData` → новый JWT. Заменяет «только HMAC» из §аутентификации.

### 12.4 Маркировка seed vs crowd (Честность / боль №2)

`BenchmarkReader` всегда возвращает `source`. UI/OG **обязан**: «По N реальным свадьбам» только для `crowd`; для `seed` — «Ориентир (YYYY)». Слово «реальные» никогда не на seed. Защищает ядро позиционирования от bait-and-switch.

### 12.5 Деньги — `bigint` копейки (Code quality)

Единое представление по всему стеку, тип `Money` в `packages/shared`. Форматирование в ₽ только на границе UI. Нет float/numeric. (см. §4)

### 12.6 Оптимистичная блокировка финансов (Code quality / ядро обещания)

`budget_items` и `payments` получают поле `version`. UPDATE с `WHERE version = ?`; 0 строк → 409 «данные изменились, обновите». Защищает от тихой перезаписи суммы платежа при одновременном редактировании партнёром. Прочие поля (чеклист, профиль) остаются last-write-wins (§7).

### 12.7 Идемпотентность `spend_facts` + 152-ФЗ-удаление (Code quality / моат / комплаенс)

Ровно один факт на `(project_id, category_id)`, UNIQUE, upsert по итоговой сумме; правка/удаление платежа → пересчёт/удаление факта. Одна свадьба = один вклад в агрегат (нет дублей). `project_id` хранится для upsert/удаления, **исключён из агрегатов** → при удалении проекта факты вычищаются (право на удаление по 152-ФЗ исполнимо), анонимность держит k-anon. (см. §4, закрывает противоречие 11.4 ↔ обезличенность)

### 12.8 Rate-limit анонимных эндпоинтов (Безопасность / производительность)

Анонимный расчёт сметы, OG-рендер и `/showcase` — самая открытая поверхность. v1: rate-limit по IP/preset через Redis; OG-картинка кэшируется по preset-hash; витрина кэшируется (12.10). Принимаем, что seed-сетка де-факто публична.

### 12.9 Дедуп каналов напоминаний (Надёжность)

Mini App-fallback (11.5) — это **view статуса той же сущности reminder**, а не независимый триггер. Единый `ack`/`done` гасит оба канала. Дедлайн сообщается один раз. Исключает спам на финансовых/ЗАГС-датах.

### 12.10 Кэш агрегатов витрины (Производительность)

`getAggregates` кэшируется в Redis (TTL ~10 мин / инвалидация после пересчёта); SSR-роуты отдают `Cache-Control`. Вирусный всплеск не доходит до БД.

### 12.11 N+1 в смете (Производительность)

`BenchmarkReader.getAggregates(slices[])` — один батч-запрос за все категории среза (с применённым k-anon-порогом), смета считается в памяти. Не вызывать покатегорийно в цикле.

### 12.12 ЗАГС как compliance-контент (Надёжность / ядро обещания)

`checklist_templates` для kind=`zags` расширяются: `source_url` (рег-источник), `review_date`, привязка к `city`. Перед запуском named owner верифицирует правила по МСК **и** СПб. Неверное правило = пропущенная дата, поэтому ЗАГС трактуется как комплаенс, не как обычный seed. (уточняет §9)

### 12.13 Фрешность seed-цен (Надёжность хука)

`price_benchmarks(source=seed)` получают `as_of_year`; UI показывает «Ориентир (2026)» (связь с 12.4). Квартальный refresh-таск с named owner — рынок растёт +20%/год, иначе смета-крючок врёт лоуболлом. (уточняет §9, §10)

### 12.14 Тестовый объём (Тесты)

Сверх §8 в v1 добавляются integration-тесты на 3 самых рисковых пути: (1) напоминание упало → `status=failed|blocked` → дедлайн виден в Mini App API; (2) `BenchmarkReader`: `count < N` не раскрывает малую выборку; (3) invite-токен expired/revoked/reused → reject. Плюс unit/integration на gap'ы из карты покрытия (auth_date, JWT-refresh, optimistic-lock 409, spend_facts upsert/удаление, камерный режим, money-форматирование, share deep-link round-trip, 152-ФЗ delete-cascade). Браузерный E2E — позже.

### 12.15 instrument-first

v1 стартует со share-петли (11.1) и метрик (11.8), чтобы forward-rate share-карточки был виден рано — это несущая гипотеза acquisition.
